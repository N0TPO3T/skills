# 交接与恢复约定

中台在首次建立运行记录、派发和故障恢复时读取。模板按实际任务删减；不为不存在的配置或证据编造值。

## 当前宿主的工具路由

先检查当前可用工具及其说明。下列名称对应 Codex 桌面环境，不能作为其他环境的可用性保证。

| 操作 | 工具 | 约束 |
| --- | --- | --- |
| 选项目 | `list_projects` | 使用真实 project ID，核对仓库与主机 |
| 找到或读取任务 | `list_threads`、`read_thread` | 用真实 ID；按需读取，不扫所有历史 |
| 新建任务 | `create_thread` | 用户须明确要求创建独立任务；遵循工具的工作区选择规则 |
| 后续派发 | `send_message_to_thread` | 保留目标原有模型设置，除非用户要求修改 |
| 进度与等待 | `wait_threads` | 使用目标 host ID、返回的 cursor；即时快照或有界等待 |
| 调度 | `automation_update` | 使用 heartbeat 并更新同一 ID；当前 schema 为准 |

创建任务异步返回时，`clientThreadId` 不能当作 `threadId` 使用。先记录创建待完成，再通过受支持的状态读取取得真实任务 ID；未解析前不再次创建同一工作包。创建成功后遵循宿主的任务入口展示要求。

如果必要工具缺失，完成可执行的准备并具体说明缺口；不要用临时子代理冒充用户可逐项验收的独立任务，也不要手写后台调度配置绕过宿主工具。

## 一份运行记录

在已有项目记录中补充以下必要信息即可；没有入口时才使用 `work/multi-session-workflow.md`。记录所在主机及绝对路径，避免不同 worktree 各自维护同名副本。默认只有中台写入。

```text
项目与根目录：
总目标、原始验收标准、当前约定版本：
操作授权、资源/重试上限、人工关卡：
中台任务 ID / host ID：
心跳 ID、已保存频率、已核实状态：

工作包 ID、目标、约定版本、依赖：
任务 ID / host ID / 工具返回的标题：
当前尝试编号、最近派发内容摘要与投递状态：
工作目录、起始代码状态、写入范围、资源：
作业主机 / ID / 命令 / 日志 / 产物：
执行：未派发 / 创建中 / 执行中 / 已提交 / 受阻
自动核验：待核验 / 通过 / 未通过
用户验收：待验收 / 已验收 / 需修改
已验证证据、未解决问题、下一步：
```

必要时给每次派发使用同一工作包下的尝试编号，或补充“已被替代”。不要把一次提示词重投当成新实验。只保留恢复、追溯或复现所需的信息，详细日志留在原位置。

## 执行任务的派发模板

将相关字段填实后作为目标任务的初始或后续消息。执行者无需加载中台规则。

```text
你负责工作包 {ID}，尝试 {编号}，约定版本 {版本}。
目标和完成标准：{具体结果及验证方式}
已验证事实与证据：{必要事实、代码或日志位置}
待验证假设及已排除原因：{明确区分，附最少证据}
工作目录、输入版本、依赖产物：{精确位置和版本}
可修改范围与集成负责人：{边界}
资源、重试限制和人工关卡：{适用约束}
产物位置：{下游和中台可访问的位置}

先核对是否已有本次尝试的作业或产物，避免重复执行。
在此工作包范围内完成必要调试；未经安排不创建其他任务或修改调度。
不要自行修改中台运行记录。需要改变约定时报告原因与证据。
长作业启动后及时记录可恢复的作业 ID、日志和命令。
提交时说明目标、实际完成内容、产物、验证命令与结果、偏差及未完成项。
尚在运行的作业明确标记为运行中；区分观察、推断和待验证假设。
结果返回当前执行任务，由中台读取；不默认主动给中台发送唤醒消息。
```

## 心跳模板

将路径和必要边界填实，通过自动化工具保存。通知偏好字段按当前工具要求设置，不用模板替代工具设置。

```text
继续当前项目的多会话工作流。读取 {技能 SKILL.md 绝对路径} 及
{运行记录所在主机和绝对路径}，核对最新用户约束、执行任务与外部作业。
先检查截止时间和预算；已到边界则先暂停同一心跳，停止新派发，再做只读收尾。
检查新结果的证据、输入版本和验收标准；自动核验通过后推进依赖已满足的工作。
派发前检查已有任务、尝试和作业，避免重复创建或启动。
按已授权范围完成必要诊断；不要扩大目标、降低标准或突破资源上限。
仅更新同一份运行记录。按阶段调整同一个心跳，核对保存结果。
无可行动变化时保持安静；重要进展、完成、失败或需要用户决策时通知，
并遵守用户另外约定的周期汇报。
全部自动核验完成后暂停心跳，提供逐项验收索引，保留执行任务和证据。
无法继续且需要用户决策时暂停派发并报告阻塞；仍在运行的已授权作业按约定监测。
```

## 恢复时的判定

| 观察 | 应采取的动作 |
| --- | --- |
| 派发成功，但运行记录未更新 | 先读取目标任务核实该次消息；补记录，不重新投递 |
| 创建返回不确定或只拿到临时 ID | 按已知项目和任务标识查找，核对内容；未排除成功前不重复创建 |
| 执行任务结束回答，后台训练仍运行 | 保持执行中，检查真实作业；不解除依赖 |
| 心跳重复触发，但无状态变化 | 核对一次后等待，不创建新任务、不重启作业 |
| 旧约定的结果迟到 | 与当前约定比较，仅重验受影响部分；不覆盖新状态 |
| 两个就绪任务竞争同一资源 | 串行或明确隔离，资源可用后再启动 |
| 用户直接给执行任务补充要求 | 中台读取后核对影响；将明确指令同步到约定，消除冲突再派发相关工作 |
| 单个工作包受阻 | 记录证据与所需决策，继续不依赖它的已授权工作 |
| 无法读取主机或作业状态 | 保留未知状态并恢复连接；不把失联认定为失败，不重复启动 |
| 已核验分支完成，但尚未集成 | 检查下游能否使用确切产物；需要集成则按授权集成并做相关验证 |
| 所有工作自动核验通过 | 暂停调度并交付；用户验收继续保持待验收 |

恢复先核实中台所有权和最近用户变更。必要时从本记录及证据指针恢复上下文，不完整导入所有执行对话。不要把这些规则宣称为系统级恰好一次投递或崩溃恢复保证；需真实运行验证。
