# Multi-session Workflow

让 Codex 按既定计划协调独立执行任务，定时继续工作，并留下逐项可检查的验收入口。

这是一个以中文编写的 Codex skill。中台负责派发、恢复和核验；每个执行任务对应一个可验收成果，保留自己的调试上下文；心跳回到同一个中台继续推进。

## 运行要求

- 宿主必须提供真实的独立线程/任务创建、读取、消息发送及定时心跳（heartbeat）能力。当前工具路由面向 Codex 桌面环境，安装 skill 不会自动为 CLI 或其他环境补上这些工具；不能仅凭安装成功就认为通用 OMP 环境可执行此工作流。
- 本地任务需要主机、应用和项目目录保持可用；长时间训练等作业需要环境已有的可靠后台运行方式。
- 中台和全部执行、复核任务必须绑定同一个已登记的 Codex 项目。Git worktree 可以不同，但 `projectId` 必须一致；从项目外发起时先建立项目内中台。
- 启动时明确目标、完成标准、项目位置、资源范围及可自主执行的操作。已有授权会沿用。

## 安装与使用

本技能集中维护于 [skills/multi-session-workflow](https://github.com/N0TPO3T/skills/tree/main/multi-session-workflow)。推荐从集中仓库根目录安装：

```sh
git clone https://github.com/N0TPO3T/skills.git
cd skills
python install.py multi-session-workflow
```

默认目标为 `~/.agents/skills`，可加 `--dest <skills-root>` 指定宿主识别的技能根目录，不覆盖已有目录；详情见[根 README 安装说明](../README.md)。也可以让 Codex 使用 `$skill-installer` 安装集中仓库的 `multi-session-workflow` 子目录，或者将该组件内的 `SKILL.md`、`agents/` 和 `references/` 一起放入宿主识别的 `multi-session-workflow` 技能目录。安装只复制技能文件，运行仍须满足上述宿主能力要求。

在项目任务中调用：

```text
$multi-session-workflow

按以下计划推进当前项目。允许创建独立执行任务、跨任务派发和定时心跳。
目标：……
工作包及依赖：……
验收标准：……
资源与并发上限：……
可以自主修改和集成的范围：……
需要我决策的情况：……
每 5 分钟检查进展，重要变化时通知我，完成后暂停调度。
```

也可以只讨论设计，或要求恢复已有工作流、查看验收索引；这些请求不会自动重新创建所有任务。

## 核心约定

- 按成果拆分会话，同一工作包的连续调试保留在原会话。
- 创建任务显式指定已核实的项目 ID，创建后及恢复时核对实际归属；归属未知或不一致时停止继续派发，不退回项目外任务。
- 中台接收结论和证据指针，必要时才读取详细调试记录；交接区分事实与假设。
- 一份项目运行记录保存任务、尝试、代码和配置版本、作业位置与心跳状态。
- 派发前核对已存在的任务与作业；超时或失联保留为未知，避免重复启动。
- 自动核验通过可推进下游；用户验收单独记录。需要集成的结果还要核对集成后的版本。
- 完成后暂停调度，保留任务和产物供检查。局部受阻时继续不依赖它的工作。
- 最终复核阶段先暂停心跳再检查证据；派发和等待前检查截止时间，预留暂停时间。提示词不能保证硬截止，硬截止依赖作业环境的超时机制。

权威规则见 [SKILL.md](SKILL.md)，交接模板和恢复判定见 [references/coordination.md](references/coordination.md)。

## 测试

`tests/fixtures/input.csv` 是小规模测试输入。真实流程需要在支持上述工具的宿主中运行：

1. 在一个已登记的测试项目中创建中台和两个独立执行任务 A、B；从宿主读取三个任务的 `projectId`，核实一致。
2. A 生成 `normalized.json`，包含 `schema_version: 1`、原始 CSV 的 `source_sha256` 和按原顺序排列的 `rows`；每行有字符串 `id`、整数 `value`。
3. 中台核验 A，保存每分钟一次的心跳并结束初始轮次。
4. 由真正的定时唤醒派发 B；B 生成 `summary.json`，包含 `schema_version: 1`、`normalized_sha256`、`count`、`sum` 和 `mean`。
5. 更新同一个心跳为最终复核阶段；再次真实唤醒时先暂停心跳，再确认没有重复派发或重写已完成产物。检查工具调用顺序及保存的暂停时间，不能仅依据任务自报通过。

从 `skills/multi-session-workflow` 组件目录运行下面的命令独立检查产物；产物目录中应包含原始 `input.csv` 及两个 JSON 文件：

```sh
python3 tests/verify_smoke.py /path/to/test-run
```

该脚本只验证数据和来源哈希，不能代替对任务历史、真实心跳及重复派发行为的检查。测试时保存这些证据在本地，不把账号、会话 ID 或机器路径提交到公开仓库。

### 2026-09-04 实测结果

在本地 Codex 桌面环境中，以一个项目外独立中台和两个执行任务完成过一次真实试跑。首次发布前由父任务再次核对产物、执行历史和保存的调度状态。这次历史试跑没有验证本次新增的同一项目约束。

| 检查 | 结果 |
| --- | --- |
| A 的规范化结果与原始字节哈希 | 通过 |
| 初始轮次结束后，由第一次真实心跳派发 B | 通过 |
| B 的依赖哈希、条数、总和与均值 | 通过：4 条、17、4.25 |
| 更新同一个心跳，第二次真实唤醒只读重查 | 通过 |
| 重查没有新增执行任务或重写产物，随后暂停心跳 | 通过 |
| 向 A、B 发送同一尝试的重复交付请求，并行只读复核 | 通过；两个执行轮次时间重叠，三个文件的哈希、修改时间及大小未变 |
| 校验脚本拒绝错误汇总和修改后的原始输入 | 通过 |
| 在记录的截止时间之前暂停 | **未通过：晚了 12.703 秒** |

心跳已暂停，执行任务和原始证据保留在测试主机；公开仓库不包含机器路径、会话 ID 或账号凭据。

历史结果是“功能链路通过，严格时限未通过”。工具历史显示最后一次唤醒先等待执行结果，再暂停调度，暂停晚于截止时间 12.703 秒。

本次修订将最终复核阶段改为先暂停同一心跳，再读取详细状态、等待或复核；提示词开头携带阶段和截止边界，派发与等待前再次检查剩余时间并预留暂停余量。同时加入中台、执行和复核任务必须使用同一 `projectId` 的规则。

本次修订未运行复测。同项目约束和调整后的截止处理均为**已修改、未复测**，历史失败保留原结果。心跳无法保证准时送达，需要硬超时的作业仍应使用运行环境自己的超时或预算控制。

本次没有验证应用重启、主机离线、崩溃恢复、并发写冲突、worktree 集成、GPU 长作业或多天运行。普通周期复查没有重复派发，不等于已证明故障条件下的恰好一次投递。
